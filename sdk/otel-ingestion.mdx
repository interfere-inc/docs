title: "OpenTelemetry ingestion"
description: "Send traces, logs, and metrics from an OpenTelemetry Collector or native exporter."
---

Send telemetry to Interfere using your existing OpenTelemetry instrumentation. You can export through a Collector or directly from your service, without installing an Interfere SDK or creating an app. Every workspace accepts OpenTelemetry data, so there is no connection to enable first.

## Create a telemetry key

Open [Services](https://interfere.com/~/*/services) and select **Set up OpenTelemetry**. The dialog shows the Collector exporter configuration and links to **Manage Workspace keys**. In [Developer settings](https://interfere.com/~/*/settings/developer), create a workspace API key with the **Send telemetry** permission, or use an existing key with that permission. Its API scope is `org:telemetry:write`.

Store the returned secret as `INTERFERE_TELEMETRY_KEY` in your service or Collector environment, so it stays separate from the `INTERFERE_API_KEY` secret key that an app's build uses. Keep this workspace key on the server. App public keys and release-only build keys do not provide workspace telemetry access.

You can manage and revoke the key in Developer settings. See [API keys](/integrations/api-keys) for key creation and expiration settings.

## Endpoints and authentication

Use `https://api.interfere.com/drain` as the OTLP/HTTP base endpoint. The intake accepts protobuf or OTLP JSON, with optional gzip compression. Configure an HTTP exporter; this endpoint does not accept OTLP/gRPC.

| Signal  | HTTP endpoint                                |
| ------- | -------------------------------------------- |
| Traces  | `https://api.interfere.com/drain/v1/traces`  |
| Logs    | `https://api.interfere.com/drain/v1/logs`    |
| Metrics | `https://api.interfere.com/drain/v1/metrics` |

Authenticate each request with the workspace key:

```http
Authorization: Bearer YOUR_WORKSPACE_TELEMETRY_KEY
```

The `x-api-key` header also accepts the same secret. The key selects the workspace; resource attributes identify the service sending data.

## Export through a Collector

If your applications already export to a Collector, keep that setup and add this exporter to its configuration:

```yaml
exporters:
  otlphttp/interfere:
    endpoint: "https://api.interfere.com/drain"
    headers:
      Authorization: "Bearer ${env:INTERFERE_TELEMETRY_KEY}"
```

Add `otlphttp/interfere` to the `exporters` list in each traces, logs, or metrics pipeline you want to send. Keep the pipeline's existing receivers, processors, and other exporters. Defining the exporter alone does not enable it.

The Collector appends the signal path to the base endpoint. See the [OTLP HTTP exporter configuration](https://github.com/open-telemetry/opentelemetry-collector/tree/main/exporter/otlphttpexporter) for batching, queue, timeout, and retry options.

## Export directly from a service

For an OTel SDK that supports standard exporter environment variables, configure your service before it starts:

```bash
export OTEL_SERVICE_NAME="checkout-api"
export OTEL_EXPORTER_OTLP_ENDPOINT="https://api.interfere.com/drain"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer%20${INTERFERE_TELEMETRY_KEY}"
export OTEL_RESOURCE_ATTRIBUTES="service.namespace=commerce,deployment.environment.name=production,service.version=1.2.3"
```

Supply `INTERFERE_TELEMETRY_KEY` through your secret manager. `%20` encodes the space after `Bearer` in the exporter header setting.

These variables configure exporters that your application initializes; they do not install instrumentation or enable every signal. Configure the trace, log, and metric exporters you need through your language's [OpenTelemetry setup](https://opentelemetry.io/docs/languages/), and flush buffered telemetry during graceful shutdown.

Signal-specific settings override the shared settings. For example, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` must contain the full URL ending in `/drain/v1/traces`. Check for existing endpoint and header overrides when changing destinations. See [OTLP exporter configuration](https://opentelemetry.io/docs/languages/sdk-configuration/otlp-exporter/).

Use one export path per signal to avoid sending the same records both directly and through a Collector. For Next.js apps that already use the Interfere SDK, see [OpenTelemetry composition](/sdk/opentelemetry).

## Node.js

Node.js services, workers, and scripts send telemetry through the OpenTelemetry Node.js SDK. Set the exporter environment variables from [Export directly from a service](#export-directly-from-a-service), then install the SDK, auto-instrumentations, and the OTLP/HTTP protobuf trace exporter:

<CodeGroup>

```bash npm
npm install @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node @opentelemetry/exporter-trace-otlp-proto
```

```bash pnpm
pnpm add @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node @opentelemetry/exporter-trace-otlp-proto
```

```bash Yarn
yarn add @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node @opentelemetry/exporter-trace-otlp-proto
```

```bash Bun
bun add @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node @opentelemetry/exporter-trace-otlp-proto
```

</CodeGroup>

Create `instrumentation.mjs`:

```js instrumentation.mjs
import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-proto";

export const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter(),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
```

Load this module before any application code so the instrumentations can patch the libraries your app imports. For a CommonJS build, preload it with `node --import ./instrumentation.mjs dist/main.js`. For an ESM build, also configure the [OpenTelemetry ESM loader hook](https://opentelemetry.io/docs/languages/js/getting-started/nodejs/). If your app already registers an OpenTelemetry provider, add the exporter to that provider instead of starting a second one.

Await `sdk.shutdown()` in your application's graceful shutdown handler, after it stops accepting new work, so buffered spans flush before the process exits. For a short-lived script, await it before the script ends.

Auto-instrumentation records request spans but does not report every error your code catches. Record caught exceptions on the active span and set its status to `ERROR`, creating a span when none is active:

```ts
import { SpanStatusCode, trace } from "@opentelemetry/api";

const tracer = trace.getTracer("checkout-api");

export function reportError(error: Error) {
  const active = trace.getActiveSpan();
  const span = active ?? tracer.startSpan("application.error");

  span.recordException(error);
  span.setStatus({ code: SpanStatusCode.ERROR });

  if (!active) {
    span.end();
  }
}
```

To trace an operation of your own, use `tracer.startActiveSpan()` and end the span when the operation finishes. The trace exporter above sends traces only; configure log and metric exporters separately if you need those signals.

<Note>
  `@interfere/node`, `@interfere/nest`, and `@interfere/elysia` are retired. Installed versions keep
  sending data, and new setups use OpenTelemetry. When migrating, replace `withSpan` with
  `tracer.startActiveSpan()`, replace `captureError` with `reportError`, and remove the retired
  package once the service appears on the Services page.
</Note>

## Identify services and deployments

Set resource attributes in the application so a Collector forwarding multiple services retains each service's identity.

| Attribute                     | Use                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `service.name`                | A stable service name, such as `checkout-api`. Include it so Interfere can discover the service. |
| `service.namespace`           | An optional grouping, such as `commerce`, that distinguishes services with the same name.        |
| `deployment.environment.name` | The deployment environment, such as `staging` or `production`.                                   |
| `service.version`             | The deployed version or Git commit SHA, so you can identify which code produced the telemetry.   |

Keep the service name and namespace consistent across deployments. Each discovered service appears on the [Services](/product/services) page. Discovery does not attach a service to an app or upload source maps.

Services deployed as [Cloudflare Workers](/integrations/cloudflare-workers) can be [linked to an app](/product/services#link-a-service-to-an-app), which charts their traces on the app's **Overview** under **Linked OpenTelemetry services**. Logs and metrics from linked services are not charted yet.

## Verify ingestion

Generate a request in your service, allow its exporter to flush, then check [Services](https://interfere.com/~/*/services) for the service name. Check the exporter or Collector logs for rejected records or connection errors.

An HTTP `200` response can include OTLP partial-success details. Check those details before treating the entire batch as accepted.

| Response | Check                                                                         |
| -------- | ----------------------------------------------------------------------------- |
| `401`    | The workspace key, its expiration, and the `org:telemetry:write` scope.       |
| `413`    | Reduce the export batch size.                                                 |
| `415`    | Use `application/x-protobuf` or `application/json` with a valid OTLP payload. |
| `503`    | Retry with backoff, respecting `Retry-After` when present.                    |
